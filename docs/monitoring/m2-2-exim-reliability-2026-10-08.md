# M2.2 — EXIM scheduled reliability evidence (read-only)

**Status:** implementation candidate; require exact-head GitHub CI, review and human squash merge. **Not yet a Day-7, Day-14 or Day-30 success claim.** Those milestones require actual days to pass.

## Proven operating baseline

M2.1's original explicit baseline on [run #37800436243](https://github.com/VSSpowerlifting/strategic-materials-policy-tracker/actions/runs/37800436243) at 2026-10-08 15:23 UTC was verified healthy: 20 dated full releases, HTTP 200, no coverage gap, zero "new" items claimed, state artifact `smpt-exim-state-37800436243-1` and corresponding report artifact both uploaded.

[Restored replay #37801575996](https://github.com/VSSpowerlifting/strategic-materials-policy-tracker/actions/runs/37801575996) independently downloaded the preceding state artifact and scanned 20 releases at HTTP 200, `baseline=false`, zero new/revised and no reported coverage gap; both new run-specific artifacts were uploaded. **Two same-day manual green runs do not constitute seven days of reliability.**

The EXIM monitor already schedules daily `14:07 UTC` and enforces `health=ok` and `possibleWindowGap=false`. GitHub cron scheduling does not prove that a run happened, and workflow success without a complete state/report pair is not an acceptable operational observation.

## M2.2 audit architecture

- **Separate completed-run trigger:** `.github/workflows/exim-reliability-evidence.yml` runs following the `SMPT EXIM shadow monitoring` workflow's completion, restricted to `main` in this same repository. It checks out trusted `main`, has **contents:read** and **actions:read** only, and has no secret except a read-only-scoped built-in GitHub token. It neither fetches EXIM pages nor invokes `monitor:exim`; no mail, GH writes, database, private inbox or publish behavior.
- **Official evidence surface:** `scripts/audit-exim-reliability.ts` uses only the fixed GitHub Actions REST endpoints for the EXIM workflow's `main` runs and each successfully completed run's artifact list. Search is bounded to 10 pages of 100 runs and **must** find the immutable already-verified baseline run ID `37800436243`. Absent/truncated metadata or unknown trigger identity fails rather than inventing success.
- **Run health:** a scheduled day counts **only** when a completed, successful EXIM run has **both** unique, nonexpired artifacts named `smpt-exim-state-RUN-ATTEMPT` and `smpt-exim-report-RUN-ATTEMPT`. Source health/no-window-gap is enforced by the EXIM workflow's own health gate; artifact names alone do not independently validate internal JSON. Failed runs and absent/expired artifacts are explicit exceptions, not zero-activity days.
- **Calendar maturity:** baseline day **2026-10-08 UTC** is Day 0. Days 1–7, 1–14 and 1–30 require distinct verified **scheduled** UTC observation days. Manual `workflow_dispatch` runs, including the Day-0 restored replay, are visible but **never substitute** for scheduled days. A milestone stays `pending` on its final day if that day's expected scheduled job has not finished; from the following UTC day, any missing/degraded scheduled day makes it `incomplete`. An early missing day is still noted while the milestone is pending. A milestone is `passed` only after every required day is verified.
- **Evidence receipt, not longitudinal state:** the audit writes `audit.json` and `summary.md` inside an isolated `.monitor-exim-reliability/` directory on its runner and uploads `smpt-exim-reliability-RUN-ATTEMPT` for 30 days. These are metadata/operational evidence only. The EXIM source observation's own artifacts, schedule, health gating and hashed identity continuity are **unchanged**. No M1, candidate, policy or financial data are touched.
- **Failure semantics:** the separate reliability job fails if the just-completed EXIM run was red, its artifact pair is missing, a matured 7/14/30-day scheduled evidence window is incomplete, or GitHub evidence fetch/validation fails. It can be red without altering the source monitor's outcome. A scheduled EXIM failure itself remains red at the original workflow too.
- **Maintenance:** the audit's window cannot outrun GitHub's 30-day artifact retention indefinitely; long-term immutable receipts will require later storage design. It does not guarantee that source changes between runs were captured, that the upstream EXIM site publishes exhaustively, or that human/editorial false-positive review has been completed.

## Acceptance and milestones

1. Exact-head GitHub CI must pass `npm run validate`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Tests explicitly cover two manual Day-0 runs, exact 7/14/30 scheduled days, missing days, manual non-substitution, failed/missing/expired artifact cases, same-day repeats, provenance refusal, and absence of write-authority in the new workflow. The CLI `npm run audit:exim -- --check-runtime` must work offline without token or filesystem changes.
2. After merge, **do not dispatch another EXIM bootstrap**. Leave its existing daily cron untouched. Observe the first **scheduled** EXIM completion, then inspect its automatic **SMPT EXIM reliability evidence** companion run. Confirm evidence receipt, scheduled run/day count, and `pending` maturity statuses. A manual run is unnecessary simply to exercise the reliability code.
3. Day-7 may mature on **October 15 UTC**, Day-14 on **October 22**, Day-30 on **November 7**, assuming each required daily scheduled run has completed with the expected artifacts. Later GitHub cron delays and skipped runs must be reported rather than averaged away. Day-30 requires attention to 30-day artifact expirations; a durable retention solution is a later separate phase.
4. Only after healthy days accumulate consider EXIM's separate **human-gated editorial ingestion** design. This M2.2 PR deliberately does not unify schemas or migrate review decisions. Keyword-only matches are not official project or financing classification.

**Operational recommendation:** keep the M2.1 collection schedule unchanged while running M2.2 as an evidence-only companion. Investigate anomalies before any new source activation or classification automation.
